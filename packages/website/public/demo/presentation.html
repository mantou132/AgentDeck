让我们把时钟拨回到几年前。为什么很多团队调研过 Web Components，最后还是默默回到了 React 或 Vue？

【翻页】

---

曾经的痛点

为什么原生 Custom Elements 很难直接写复杂业务？

样板代码繁琐

属性监听与反射（observedAttributes）需手动类型转换与序列化，缺乏静态类型约束。

DOM 手动更新

缺少响应式状态与细粒度模板渲染，状态更新依赖手动操作真实 DOM，极易产生漏洞与性能瓶颈。

样式与封装摩擦

Shadow DOM 虽隔离了样式，但在全局设计规范共享、动态主题换肤和跨组件穿透上充满心智摩擦。

【幻灯片显示三栏卡片】

原生 Custom Elements 最大的问题，不是标准不能用，而是**标准只提供了最底层的积木，没有提供舒适的工程化体验**。

【点击出现第一条：样板代码繁琐】 第一，样板代码极多。写过原生自定义元素的同学都知道，想要监听一个属性变化，你得先在 `observedAttributes` 数组里声明字符串，再在 `attributeChangedCallback` 里手动写 `if-else` 或 `switch`，自己做字符串转布尔、转数字、转对象，不仅繁琐，而且完全失去了 TypeScript 的类型推导与编译期保障。

【点击出现第二条：DOM 手动更新】 第二，没有内置的响应式与模板机制。原生标准只告诉你“元素被挂载了”、“属性变了”，至于属性变了之后怎么更新 DOM？标准留给你自己用 `this.innerHTML = ...` 或者一系列 `document.createElement` 去拼。面对稍微复杂的列表渲染、条件判断，手写 DOM 操作极其痛苦，稍微不注意就会引发性能退化和内存泄漏。

【点击出现第三条：样式与封装摩擦】 第三，Shadow DOM 的双刃剑。Shadow DOM 提供了完美的样式隔离，但在实践中，跨组件共享全局设计规范、统一主题变量，或者外部样式局部穿透时，原生的方案充满了各种 hack，开发心智负担很重。

正因为这些痛点，过去的社区只能靠大型框架去弥补。

标准契机

现代浏览器补齐了关键拼图

ES 2023 标准装饰器

TC39 Stage 3 装饰器标准正式落地，以纯粹语言特性实现声明式组件，无需实验性 hack。

AdoptedStyleSheets

可构造样式表完美解决 Shadow DOM 间共享样式的性能开销，零成本共享设计 Token 与主题。

全平台原生性能

现代浏览器与嵌入式 WebView 均全面支持 Custom Elements v1，直接调用底层 C++ 引擎。

【幻灯片显示三大标准契机】

在最近一两年里，几个重量级的标准拼图终于全部就位：

【点击出现第一条：ES 2023 标准装饰器】 首先是 **ES 2023 标准装饰器（TC39 Stage 3）**。过去我们写装饰器依赖 TypeScript 的实验性语法或者 Babel 的转译 hack，语法飘忽不定；而现在，JavaScript 官方标准装饰器已经正式落地！这意味着我们可以用完全符合语言标准的声明式语法，来定义属性、方法和组件元数据。

【点击出现第二条：AdoptedStyleSheets】 其次是 **Constructable Stylesheets，也就是 AdoptedStyleSheets**。以前每个 Shadow Root 都要复制一份 &lt;style&gt; 标签，内存开销巨大；现在，一个样式表对象可以在多个组件乃至全局之间零拷贝共享，动态换肤、Token 继承变得比传统 CSS-in-JS 还要轻快。

【点击出现第三条：全平台原生性能】 最后，所有的主流浏览器、移动端 WebView、桌面端嵌入式环境（Chromium、Safari、Firefox、Webkit），对 Custom Elements v1 的原生支持都已经到了极其成熟稳定的阶段。

既然浏览器的底层能力已经完全武装到了牙齿，我们为什么还要在上面套一层厚重的虚拟 DOM 运行时呢？

基于这个思考，我写了 **Gem**。

---

设计哲学

Gem 的核心原则

紧跟标准，零私有运行时

继承原生 GemElement (HTMLElement)，无虚拟 DOM 层，让浏览器做最擅长的事。

声明式与细粒度响应式

基于标准 ES 装饰器与微任务批处理，精准更新变动 DOM，告别全树 Diff 性能负担。

极致轻量与零妥协 TS

框架核心仅数 KB；TypeScript 优先，从属性、事件到模板提供第一等公民的静态类型安全。

【幻灯片显示三大设计哲学卡片】

Gem 的设计哲学非常纯粹，可以概括为三句话：

【点击出现第一条：紧跟标准，零私有运行时】 第一，**紧跟标准，零私有运行时**。在 Gem 里，每一个组件就是一个普通的 ES 类，继承自 `GemElement`，而 `GemElement` 本质上就是原生的 `HTMLElement`。它没有自己造一套闭门造车的虚拟节点树，没有庞大的 Synthetic Event 合成事件系统，直接把执行权交给浏览器引擎。

【点击出现第二条：声明式与细粒度响应式】 第二，**声明式与细粒度响应式**。我们不需要回到手动操纵 DOM 的石器时代。Gem 基于模板标签和微任务队列，实现了真正的细粒度更新：哪里的数据变了，就精确打补丁到对应的真实 DOM 节点上，完全避免了每次更新自顶向下对比整棵树的性能损耗。

【点击出现第三条：极致轻量与零妥协 TS】 第三，**极致轻量，TypeScript 优先**。整个框架核心只有几 KB，但从属性定义、事件传递到模板类型推断，全流程享受第一等公民的静态类型安全。

说起来很抽象，我们直接来看一段代码是怎么写的。

开发体验

清晰、直观的组件语法

输入与状态

@property 属性响应式同步
@state 映射 CSS 状态伪类
createState 管理私有状态

渲染与生命周期

@template 声明模板与 html 标签
@memo / @effect 显式依赖追踪
@adoptedStyle 高效共享样式表

全局状态与事件

createStore / @connectStore 状态跨组件联动
@emitter / @globalemitter 规范事件派发

【幻灯片显示三组核心特性卡片】

如果你熟悉 React Hooks 或者 Vue Composition API，看 Gem 的代码会感到极度的亲切和自然，甚至更加清晰：

【点击出现第一组：输入与状态】 - **输入与属性**：一个 `@property` 装饰器，就能直接把类属性与元素属性双向同步，不仅自动做类型转换，还会自动触发响应式重绘；用 `@state` 可以直接将组件内部状态映射为 CSS 自定义状态伪类；用 `createState` 轻松管理私有状态。

【点击出现第二组：渲染与生命周期】 - **渲染与逻辑**：用 `@template` 定义渲染函数，内部直接写现代的模板字符串 `html\`...\``。依赖跟踪用 `@memo` 和 `@effect`，清清楚楚地通过依赖数组控制副作用，返回清理函数；通过 `@adoptedStyle`，你可以轻松把公共样式挂载到当前组件的 Shadow DOM 中，零运行时开销。

【点击出现第三组：全局状态与事件】 - **全局状态与通信**：多组件状态共享不需要冗长的 Redux 或 Pinia，一个 `createStore` 创建响应式 Store，在组件上挂一个 `@connectStore` 装饰器，组件就会在 Store 数据变动时自动重绘。组件对外通知用 `@emitter`，如果需要跨 Shadow DOM 向外层广播，一个 `@globalemitter` 就搞定了。

没有魔法，全都是标准的 ECMAScript 语法。

工程化与生态

不只一个运行时，而是一整套生态

unplugin-gem

支持 Vite、Rsbuild、Webpack，实现 Gem API 与自定义组件自动按需导入与无缝 HMR。

Duoyun UI & Tap UI

开箱即用的原生 UI 库，分别专为桌面端与移动端场景量身打磨，交互细腻、轻巧顺滑。

@gem-bind/*

官方提供 ECharts、Mermaid、Marked、LaTeX 等高频生态的 Custom Elements 快速包装。

【幻灯片显示生态组成】

有的同学可能会问：“单有框架还不够，现代开发需要工程化工具，需要组件库，Gem 的生态怎样？”

Gem 从一开始就考虑到了完整的工程化闭环：

【点击出现第一条：unplugin-gem】 首先是构建工具。我们开发了 `unplugin-gem`，支持 Vite、Rsbuild、Webpack 等所有主流构建工具。它支持**全自动按需导入**，写代码时你根本不需要手动 `import { GemElement, html, ... }`，开箱即用，同时提供了完美的开发期 HMR（热更新）体验。

【点击出现第二条：Duoyun UI & Tap UI】 其次是组件库。我们拥有专为桌面端打造的 **Duoyun UI**，以及专为移动端打造的 **Tap UI**。它们完全由 Gem 编写，这意味着它们是纯正的原生 Web Components，拥有极高质量的交互手感与可定制性。

【点击出现第三条：@gem-bind/*】 最后是流行工具的绑定。无论你想在应用中嵌入 ECharts 图表、Mermaid 流程图、Marked Markdown 渲染，还是 LaTeX 数学公式，我们都提供了官方的 `@gem-bind/*` 包，把复杂的第三方库封装成一个简单干净的原生自定义元素。

生产指标

极致的轻量与性能

< 10 KB运行时 gzip 体积
0 VDOM零虚拟 DOM 开销
100%标准 Web Components

冷启动更快、内存占用更低、跨应用嵌入毫无包袱。

【幻灯片显示三大数字指标】

最直接的收益就是**轻量与性能**。

【点击出现指标一：< 10 KB】 框架的核心运行时非常精简，相比动辄几十 KB 的通用框架，Gem 的体积优势在低网速环境或者资源敏感型场景下极其显著。

【点击出现指标二：0 VDOM】 没有庞大的虚拟 DOM 运行时。所有的模板编译在构建期完成，运行期依托浏览器的原生模板与细粒度节点替换，没有大树对比的内存开销与 CPU 毛刺。

【点击出现指标三：100% 原生标准】 每一个产出元素，都是浏览器标准认可的 Custom Element。它在浏览器 DevTools 里是一个干干净净的自定义标签，没有冗杂的包裹层。

架构收益

在复杂生产应用中的实践价值

真正的跨宿主与微前端

桌面客户端（Tauri）、浏览器扩展、任意宿主微前端，原生标签即插即用，绝无运行时多实例冲突。

天然的沙箱与样式隔离

Shadow DOM 彻底隔绝样式污染，无需复杂的 CSS Modules 哈希化，样式安全有保障。

穿越框架周期的代码资产

框架潮起潮落，但浏览器标准永存。基于 Gem 开发的组件将长久稳定运行在标准 Web 平台之上。

【幻灯片显示三项架构收益】

在更宏观的架构层面上，Gem 带来了三个很多传统框架无法比拟的优势：

【点击出现第一条：真正的跨宿主与微前端】 第一，**真正的跨宿主与微前端**。如果你做过跨团队协作或者微前端，你一定体会过不同 React/Vue 版本冲突、全局变量污染的痛苦。而基于 Gem 构建的组件，输出的就是原生标签。无论宿主页面用的是 Next.js、Vue 还是 Angular，直接 &lt;my-element&gt; 就能渲染，甚至作为浏览器扩展的内容注入脚本（Content Script），都天然没有多实例冲突的问题。

【点击出现第二条：天然的沙箱与样式隔离】 第二，**天然的沙箱与样式隔离**。Shadow DOM 提供了由浏览器引擎保证的样式边界。你永远不需要担心业务里的类名和外部库冲突，也不需要依赖复杂的 CSS Modules 哈希命名。

【点击出现第三条：穿越框架周期的代码资产】 第三，**穿越框架周期的资产积累**。前端圈的技术风向变化极快。今天流行的 API，明天可能就被弃用了。但 Web 标准不会死，浏览器对 Custom Elements 的支持不会推倒重来。你用 Gem 写的组件，在五年、十年后，依然是标准浏览器里可以直接运行的代码。

而是让代码活得比任何框架都更久。
